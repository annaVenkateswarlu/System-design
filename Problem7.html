Problem 7

🐌 Cache Layer Increasing Latency: 120ms → 900ms

👉 Interviewer asks:

We added a cache layer to improve performance of system but our API latency went from 120ms to 900ms.
Any idea why this happened?

💡 Key Insight:

Cache only helps when hit ratio is high and access is fast. If not, it becomes an extra bottleneck layer.

🔍 What's Going Wrong?

🔴 1. Low Cache Hit Rate

📊 What is Cache Hit Ratio?

Cache Hit Ratio measures how often your system finds data in the cache instead of going to the database.

Cache Hit Ratio = (Cache Hits) / (Total Requests)

💥 Problem:

If most requests are cache misses:

Request → Cache (miss) → DB → Response

  • 👉 You added an extra network hop (cache + DB)
  • 👉 Result = more latency instead of less

💡 Example:

  • Cache lookup: 50ms
  • DB query: 120ms
  • 👉 Total = 170ms+

Example 2:

Hit ratio = 20% ❌

👉 80% requests still go to DB + extra cache step

✅ Fix:

1. Cache frequently accessed data

🟠 2. Network Latency to Cache

💥 Problem:

If cache (like Redis) is:

  • In different region / AZ
  • Or poorly connected

👉 Cache call itself becomes slow (200–500ms)
👉 Cache becomes slower than DB

✅ Fix:

  • Keep cache close to app
  • Use same region / in-memory caching

🔵 3. Cache Stampede

💥 Problem:

  • Many keys expire at same time
  • Many requests hit DB simultaneously
  • 👉 System slows down massively

✅ Fix:

Add jitter to TTL

What is Jitter to TTL?

TTL (Time To Live) = how long data stays in cache

⚠️ Problem Without Jitter:

If you set: TTL = 60 seconds
After 60 sec → cache expires at the same moment → next request hits DB

💡 Solution:

Jitter = random variation added to TTL

Example: TTL = 60 + random(0–10) seconds

👉 Some keys expire at 61s, 65s, 68s…
👉 Requests spread out → no sudden spike ✅

Add TTL + Jitter means setting a base expiration time and adding randomness so cached data expires at different times, preventing many requests from hitting the database at once.

🟣 4. Synchronous Cache Layer Blocking

💥 Problem:

  • App waits for cache every time
  • Even when cache is slow

✅ Fix:

Use fallback logic

What is Fallback Logic?

Fallback logic means your system should not fail or wait indefinitely if the cache is unavailable—it should gracefully fall back to the database.

Fallback logic ensures the system continues to serve requests by retrieving data from the database when the cache fails or misses, instead of blocking or returning errors.

💬 One Line Answer

If latency increases after adding a cache, it usually means the cache is adding overhead instead of reducing work. This can happen due to low cache hit ratio, frequent cache misses, network latency to the cache, or poor key design.

I would first analyze cache metrics like hit rate and latency, then optimize by caching only frequently accessed data, improving key design, keeping cache close to apps in the same region, and handling cache stampede using TTL strategies + jitter and handling synchronous cache layer blocking using fallback logic.

📋 Summary

Problem Solution
Low Cache Hit Rate Cache frequently accessed data only
Network Latency to Cache Keep cache close to app, same region
Cache Stampede Add jitter to TTL
Synchronous Cache Blocking Use fallback logic to DB

🧠 Interview Tips

  • Understand the counter-intuitive nature — Cache can increase latency
  • Know the metrics — Hit rate, latency to cache
  • Explain cache stampede — TTL jitter is key
  • Fallback logic — Don't let cache block requests
  • Proximity matters — Same region, in-memory
