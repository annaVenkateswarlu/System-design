Interfaces in Java

Contracts that define behavior without implementation

Home / LLD / Interfaces

📋 What is an Interface?

An interface is a contract: a list of methods that any implementing class must provide.
It specifies a set of behaviors that a class agrees to implement but leaves the details of those behaviors up to each implementation.

Interface defines:

  • What operations are available
  • but NOT how they are implemented

Real-World Analogy

Consider a remote control. It exposes a standard set of buttons:

  • play()
  • pause()
  • volumeUp()
  • powerOff()

The person using the remote doesn't care if it controls a TV, a soundbar, or a projector, they all understand the same set of commands.

Figure 1: The remote is the interface. The devices (TV, soundbar, projector) are the implementations.

🗝️ Key Properties of Interfaces

Here are their most important characteristics:

a) Defines Behavior Without Dictating Implementation

An interface only declares what operations are expected. It doesn't define how they are carried out.
This gives freedom to implementers to provide their own version of the logic, while still honoring the same contract.

b) Enables Polymorphism

Different classes can implement the same interface in different ways. This allows your code to work with multiple implementations interchangeably.

c) Promotes Decoupling

Code that depends on interfaces is insulated from changes in the concrete classes that implement them. This makes your code easier to:

  • Extend (add new implementations without modifying existing ones)
  • Test (mock interfaces in unit tests)
  • Maintain (fewer ripple effects from code changes)

Example: Payment Gateway Abstraction

As long as all payment providers implement the PaymentGateway interface, the CheckoutService can use any of them without changing its own code.

The service depends on an abstraction (PaymentGateway), allowing multiple interchangeable implementations like Stripe, Razorpay, or PayPal, ensuring loose coupling and extensibility.

We can add a new payment implementation without modifying CheckoutService. The only requirement is that the new class implements the PaymentGateway interface. This ensures that changes are isolated to implementations and do not impact the high-level service.

Figure 2: CheckoutService depends on abstraction, multiple providers implement the interface

💻 Code Example: Payment Gateway Interface

Let's say you're designing a payment processing module that supports multiple providers like Stripe, Razorpay, and PayPal.
You don't want your business logic to depend on a specific provider. You just want a common way to initiate a payment.

PaymentGateway Interface

Java 
public interface PaymentGateway {
    void initiatePayment(double amount);
}

Implementations

Java 
public class StripePayment implements PaymentGateway {
    public void initiatePayment(double amount) {
        System.out.println("Processing payment via Stripe: $" + amount);
    }
}

public class RazorpayPayment implements PaymentGateway {
    public void initiatePayment(double amount) {
        System.out.println("Processing payment via Razorpay: ₹" + amount);
    }
}

CheckoutService

Java 
public class CheckoutService {
    private PaymentGateway paymentGateway;

    public CheckoutService(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }

    public void setPaymentGateway(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }

    public void checkout(double amount) {
        paymentGateway.initiatePayment(amount);
    }
}

Main Usage

Java 
public class Main {
    public static void main(String[] args) {
        PaymentGateway stripeGateway = new StripePayment();
        CheckoutService service = new CheckoutService(stripeGateway);
        service.checkout(120.50);  // Output: Processing payment via Stripe: $120.5

       // Switch to Razorpay
        PaymentGateway razorpayGateway = new RazorpayPayment();
        service.setPaymentGateway(razorpayGateway);
        service.checkout(150.50);  // Output: Processing payment via Razorpay: ₹150.5
    }
}

Output:

Processing payment via Stripe: $120.5

Processing payment via Razorpay: ₹150.5

Explanation

Here's the PaymentGateway interface that defines a single operation: initiate a payment with a given amount.

We created two classes that fulfill this contract: one for Stripe and one for Razorpay. Each processes payments differently, but both satisfy the PaymentGateway interface.

Figure 3: Both classes implement the same interface with different internal logic

Both classes (StripePayment, RazorpayPayment) implement the same interface, but their internal logic is completely different. StripePayment talks to the Stripe API, RazorpayPayment talks to Razorpay. The interface guarantees that both provide the initiatePayment() method, so any code that depends on PaymentGateway can work with either one.

Instead of having CheckoutService depend on StripePayment or RazorpayPayment, it depends on the PaymentGateway interface. It doesn't know or care which implementation it's using.

Look at the CheckoutService constructor. It takes a PaymentGateway, not a StripePayment. This single decision is what decouples the service from any specific provider.

The checkout() method calls initiatePayment() on whatever gateway was injected. It could be Stripe, Razorpay, a mock for testing, or a provider that doesn't even exist yet.

This pattern is called dependency injection: instead of creating its own dependencies, the class receives them from the outside. And it only works because the dependency is typed as an interface, not a concrete class.

The CheckoutService didn't change between the two calls. The only thing that changed was which implementation was plugged in.

Without Interface (Tightly Coupled Design)

Java 
class StripePayment {
   public void initiatePayment(double amount) {
       System.out.println("Processing payment via Stripe: $" + amount);
   }
}

class RazorpayPayment {
   public void initiatePayment(double amount) {
       System.out.println("Processing payment via Razorpay: ₹" + amount);
   }
}

class CheckoutService {
   private StripePayment stripePayment;
   private RazorpayPayment razorpayPayment;

   public CheckoutService() {
       stripePayment = new StripePayment();
       razorpayPayment = new RazorpayPayment();
   }

   public void checkoutWithStripe(double amount) {
       stripePayment.initiatePayment(amount);
   }

   public void checkoutWithRazorpay(double amount) {
       razorpayPayment.initiatePayment(amount);
   }
}

public class Main {
   public static void main(String[] args) {
       CheckoutService service = new CheckoutService();

       service.checkoutWithStripe(120.50);
       service.checkoutWithRazorpay(150.50);
   }
}

🚫 Problems in This Approach

  • Tight Coupling - CheckoutService directly depends on StripePayment and RazorpayPayment
  • Violates Open/Closed Principle - Every new payment → modify existing class ❌
  • Not Scalable - If you add PayPal, you must modify CheckoutService

🚀 When to Use Interfaces in LLD

Use interfaces when:

  • Multiple interchangeable implementations of the same behavior (e.g., different payment methods, storage systems, or notification channels)
  • Flexibility and scalability
  • Decouple high-level logic from low-level details, so your system remains flexible and easy to extend without modifying existing code
  • Applying SOLID principles, especially the Dependency Inversion Principle (DIP) — where code depends on abstractions, not concrete classes

📝 Key Takeaways

  • Interface = Contract that defines behavior without implementation
  • Polymorphism = Multiple implementations, same interface
  • Decoupling = Code depends on abstractions, not concrete classes
  • Dependency Injection = Receive dependencies from outside
  • SOLID Principles = DIP - Depend on abstractions
