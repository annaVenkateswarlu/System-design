🔷 Law of Demeter (LoD)

The Law of Demeter, also called the Principle of Least Knowledge, states:

"A class should only talk to its immediate friends and not to strangers."

In simple words:

👉 An object should only interact with objects it directly owns or receives, not with objects deep inside another object.

🧠 Real-Life Analogy

Imagine you want to talk to your friend's mother.

❌ Instead of:

You → Friend → Friend's Mother
and directly dealing with your friend's family details,

✅ You ask your friend:

You → Friend
and let your friend handle the rest.

❌ Example 1 (Violation of LoD)

Java 
class Engine {
   public void start() {
       System.out.println("Engine started");
   }
}

class Car {
   private Engine engine = new Engine();

   public Engine getEngine() {
       return engine;
   }
}

class Driver {
   private Car car = new Car();

   public void drive() {
       car.getEngine().start(); // ❌ Reaching inside Car
   }
}

Problem

Driver knows:

  • Car
  • Engine

If Car's internal structure changes, Driver must change too.

✅ Example 1 (Follows LoD)

Java 
class Engine {
   public void start() {
       System.out.println("Engine started");
   }
}

class Car {
   private Engine engine = new Engine();

   public void start() {
       engine.start();
   }
}

class Driver {
   private Car car = new Car();

   public void drive() {
       car.start(); // ✅ Talk only to Car
   }
}

💡 Example 2

❌ Violating Law of Demeter

Java 
class Address {
    String city;

    String getCity() {
        return city;
    }
}

class Customer {
    Address address;

    Address getAddress() {
        return address;
    }
}

class Order {
    Customer customer;

    Customer getCustomer() {
        return customer;
    }
}

Usage:

Java 
String city =
   order.getCustomer()
        .getAddress()
        .getCity();

Problem:

🔍 What Happens Internally?

Order
↓
Customer
↓
Address
↓
City

The caller knows:

  • Order contains Customer
  • Customer contains Address
  • Address contains City

This means the caller knows too much about the internal structure.
This creates tight coupling.
If Address changes, Order may break.

✅ Following LoD

Java 
class Address {

private String city;

public Address(String city) {
this.city = city;
}

public String getCity() {
return city;
}
} 

class Customer {

private Address address;

public Customer(Address address) {
this.address = address;
}

public String getCity() {
return address.getCity();
}
} 

class Order {

private Customer customer;

public Order(Customer customer) {
this.customer = customer;
}

public String getCustomerCity() {
return customer.getCity();
}
} 

public class Main {
    public static void main(String[] args) {
        Address address = new Address("Hyderabad");
        Customer customer = new Customer(address);
        Order order = new Order(customer);
        String city = order.getCustomerCity();
        System.out.println(city);
    }
}

Important: Here we noticed Customer hides Address details, we hide Customer as well.

💡 Easy Rule

If you see code like:

a.getB().getC().getD().getE();

Ask yourself:
"Does this object know too much about another object's internals?"

If yes, it's usually a Law of Demeter violation.

💡 Easy Memory Trick

Imagine classes have a social rule:

Talk to your friends, not your friends' friends.

🎤 Summary

The Law of Demeter states that an object should only communicate with its immediate collaborators and should not depend on the internal structure of other objects.
