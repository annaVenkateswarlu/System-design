🔷 Liskov Substitution Principle (LSP)

LSP is the third principle of SOLID.

It states:

"Objects of a subclass should be replaceable with objects of the superclass without affecting the correctness of the program."

Simply:

If a child class cannot properly follow the behavior/rules of the parent class, then it should not inherit from that parent. Instead, use another abstraction (like an interface).

❌ Bad Design (LSP Violation)

Parent Class (Parent/base/super class)

Java 
class Bird {
   void fly() {
       System.out.println("Bird is flying");
   }
}

The parent class is saying: "Every Bird can fly."

Child Classes (Child/derived/sub classes)

Java 
class Sparrow extends Bird {
   @Override
   void fly() {
       System.out.println("Sparrow is flying");
   }
}

class Ostrich extends Bird {
   @Override
   void fly() {
       throw new RuntimeException("Ostrich can't fly");
   }
}

Main Class

Java 
public class Main {
   public static void makeBirdFly(Bird bird) {
       bird.fly();
   }

   public static void main(String[] args) {

       Bird sparrow = new Sparrow();
       makeBirdFly(sparrow);

       Bird ostrich = new Ostrich();
       makeBirdFly(ostrich);
   }
}

Output

Sparrow is flying

Exception in thread "main"

java.lang.RuntimeException: Ostrich can't fly

Let's analyze it.

Parent Class Contract

Bird says: bird.fly(); should work for every Bird. That's the contract.

Sparrow

Java 
Bird bird = new Sparrow();
bird.fly();

Output:

Sparrow is flying

✅ Works correctly. Sparrow follows the parent's rule.

Ostrich

Java 
Bird bird = new Ostrich();
bird.fly();

Output:

Exception: Ostrich can't fly

❌ Breaks.

Why Is This an LSP Violation?

What Happened?

The method:

Java 
void makeBirdFly(Bird bird) {
   bird.fly();
}

Since the parameter type is Bird for makeBirdFly method should work for sparrow, ostrich.

Works for:

Java 
Bird sparrow = new Sparrow();

But breaks for:

Java 
Bird ostrich = new Ostrich();

Why?

Because the parent (Bird) promised: bird.fly(); should always work. But the child (Ostrich) broke that promise.

The child class (Ostrich) cannot safely replace the parent (Bird). That is exactly what LSP warns about.

The Core Problem

The inheritance relationship says: Ostrich IS-A Bird which is true.

But the code also says: Every Bird can fly which is false.

The mistake is not that Ostrich extends Bird. The mistake is putting: void fly() inside Bird.

✅ Better Design (LSP Followed)

Now let's redesign.

Bird Class

Java 
class Bird {
}

Notice: fly() is removed.

Why?
Because not every bird can fly.

Flyable Interface

Java 
interface Flyable {
   void fly();
}

Sparrow

Java 
class Sparrow extends Bird implements Flyable {

   public void fly() {
       System.out.println("Sparrow is flying");
   }
}

Ostrich

Java 
class Ostrich extends Bird {

   public void run() {
       System.out.println("Ostrich is running");
   }
}

Main Class

Java 
public class Main {

   public static void makeFly(Flyable flyable) {
       flyable.fly();
   }

   public static void main(String[] args) {

       Sparrow sparrow = new Sparrow();
       makeFly(sparrow);

       Ostrich ostrich = new Ostrich();
       ostrich.run();
   }
}

Output

Sparrow is flying

Ostrich is running

Explanation:

Now:

  • Sparrow is a Bird ✅
  • Sparrow is Flyable ✅
  • Ostrich is a Bird ✅
  • Ostrich is not Flyable ✅

No contracts are broken.

Why This Design Is Correct

Bird

├── Sparrow

└── Ostrich

means: Both are birds.

Flyable

│

└── Sparrow

means: Only Sparrow can fly.

No false promises.

No exceptions.

No broken behavior.

🧠 Simple Memory Trick

If you ever see a child class doing this:

Java 
@Override
void someMethod() {
   throw new UnsupportedOperationException();
}

or

Java 
throw new RuntimeException();

that's often a sign that the inheritance hierarchy may be violating LSP, because the child cannot honor the parent's behavior. 🚀

💡 The Easiest Way to Remember LSP

Ask yourself:

"Can I replace the parent object with the child object everywhere without breaking anything?"

If YES → LSP is satisfied.

If NO → The inheritance hierarchy is wrong.

🎤 Summary

LSP says that if a child class cannot completely fulfill the behavior promised by its parent, then inheritance is the wrong relationship. Move that behavior into a separate abstraction (often an interface) so only the appropriate classes implement it.

If Child cannot fully behave as Parent, then Child should not inherit from Parent.
