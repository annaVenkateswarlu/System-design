🔷 Decorator Design Pattern

The Decorator Pattern is a Structural Design Pattern.

Add new functionality to an object dynamically without modifying its existing code.

Instead of extending a class through inheritance, it wraps the original object inside another object that adds the new behavior.

It's particularly useful in situations where:

  • You want to extend the functionality of a class without subclassing it.
  • You need to compose behaviors at runtime, in various combinations.
  • You want to avoid bloated classes filled with if-else logic for optional features.

Real-World Analogy

Think of a plain coffee. Now add milk. Now add sugar. Each addition enhances the original but doesn't change the base.

The Decorator Pattern works the same way: stacking behaviors while keeping the core intact.

💡 Key Insight: Just like you can add milk, sugar, whipped cream, caramel, or any other topping to coffee in any combination, the Decorator Pattern lets you add features to objects in any combination at runtime.

Problems With Beginner Approach

Problem 1: Class Explosion

For 3 toppings:

MilkCoffee
SugarCoffee
WhippedCreamCoffee
MilkSugarCoffee
MilkWhippedCreamCoffee
SugarWhippedCreamCoffee
MilkSugarWhippedCreamCoffee

Already 7 classes.

Suppose tomorrow we add: Caramel

Now combinations explode.

MilkCaramelCoffee
SugarCaramelCoffee
MilkSugarCaramelCoffee
WhippedCreamCaramelCoffee
...

Dozens of classes.

Problem 2: Violates Open/Closed Principle

Every new topping requires creating new classes.

Problem 3: Not Dynamic

if Customer wants: Milk + Milk + Sugar

Need another class:

DoubleMilkSugarCoffee Class 
class DoubleMilkSugarCoffee {
}

Again more classes.

Decorator Solution

Instead of:

Bad Approach 
class MilkSugarWhippedCreamCoffee {
}

we do:

Decorator Approach 
Coffee coffee = new WhippedCreamDecorator( new SugarDecorator( new MilkDecorator( new SimpleCoffee() ) ) );

💡 Key Insight: With Decorator, we wrap objects layer by layer. Each decorator adds its own behavior and delegates to the wrapped object. This gives us infinite combinations with just a few classes.

Complete Decorator Implementation

Complete Decorator Implementation 
// Component interface
interface Coffee {
    double getCost();
    String getDescription();
}

// Concrete component
class SimpleCoffee implements Coffee {
    
    @Override
    public double getCost() {
        return 1.00;
    }

    @Override
    public String getDescription() {
        return "Simple coffee";
    }
}

// Abstract decorator
abstract class CoffeeDecorator implements Coffee {
    
    protected final Coffee inner;

    public CoffeeDecorator(Coffee inner) {
        this.inner = inner;
    }
}

// Concrete decorators
class MilkDecorator extends CoffeeDecorator {
    
    public MilkDecorator(Coffee inner) {
        super(inner);
    }

    @Override
    public double getCost() {
        return inner.getCost() + 0.50;
    }

    @Override
    public String getDescription() {
        return inner.getDescription() + ", milk";
    }
}

class SugarDecorator extends CoffeeDecorator {
    
    public SugarDecorator(Coffee inner) {
        super(inner);
    }

    @Override
    public double getCost() {
        return inner.getCost() + 0.20;
    }

    @Override
    public String getDescription() {
        return inner.getDescription() + ", sugar";
    }
}

class WhippedCreamDecorator extends CoffeeDecorator {
    public WhippedCreamDecorator(Coffee inner) {
        super(inner);
    }

    @Override
    public double getCost() {
        return inner.getCost() + 1.00;
    }

    @Override
    public String getDescription() {
        return inner.getDescription() + ", whipped cream";
    }
}

// Client
public class CoffeeShopDemo {
    public static void main(String[] args) {
        
        // Order 1: Simple coffee
        Coffee order1 = new SimpleCoffee();
        System.out.printf("Order 1: %s | $%.2f%n", order1.getDescription(), order1.getCost());

        // Order 2: Coffee with milk and sugar
        Coffee order2 = new SugarDecorator(new MilkDecorator(new SimpleCoffee()));
        System.out.printf("Order 2: %s | $%.2f%n", order2.getDescription(), order2.getCost());

        // Order 3: Coffee with double milk, sugar, and whipped cream
        Coffee order3 = new WhippedCreamDecorator( new SugarDecorator(new MilkDecorator(new MilkDecorator(new SimpleCoffee()))));
        System.out.printf("Order 3: %s | $%.2f%n", order3.getDescription(), order3.getCost());
    }
}

Notice how MilkDecorator is applied twice in Order 3. This is perfectly valid. Each decorator is independent, and stacking the same one multiple times adds its cost again.

With inheritance, you would need a separate DoubleMilkSugarWhippedCreamCoffee class. With Decorator, you just wrap it twice.

🧠 Real World Example

Suppose notifications.

Base : Notification

Need:

  • Email Notification
  • Email + SMS
  • Email + SMS + WhatsApp

Decorator can wrap notifications and add channels dynamically.

4️⃣ When To Use

✅

Need to Add Features Dynamically

Example:
Coffee toppings
Notification channels
Logging
🎯

Many Feature Combinations Exist

Decorator prevents class explosion.
🔓

Open for Extension

Need new functionality without changing existing classes.

5️⃣ When NOT To Use

⚠️

Only One or Two Variations Exist

Simple inheritance is enough.
🔍

Object Structure Must Remain Simple

Too many decorators can become hard to debug.
⚡

Performance Is Extremely Critical

Multiple wrappers add extra calls.

Advantages

✅ Add functionality dynamically

✅ Avoid class explosion

✅ Supports OCP

✅ Flexible combinations

✅ Reusable decorators

Disadvantages

❌ Many small classes

❌ Debugging becomes harder

❌ Object structure becomes deeper

🎯 Summary

Decorator Pattern is a Structural Design Pattern that allows behavior to be added to an object dynamically by wrapping it inside decorator objects.

Instead of creating many subclasses for every possible feature combination, decorators add functionality incrementally while keeping the original class unchanged.

This pattern is particularly useful when you need to extend functionality without modifying existing code, avoid class explosion, and support flexible feature combinations at runtime.
