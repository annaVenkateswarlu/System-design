🔁 Idempotency - Speed Through Strategic Storage

1️⃣ What is it?

An operation is idempotent if :
Performing it multiple times produces the same result as performing it once.

Doing it once or 10 times → result stays same.

Mathematically:

f(f(x)) = f(x)

📊 How idempotent operations produce same results

🧠 How Idempotency is Implemented

• Client sends Idempotency-Key
• Server stores request result
• If same key appears again : Return previous result
• Else : Don't execute again

2️⃣ Why Does It Exist? (What problem does it solve?)

Idempotency solves:

  • 🔄 Duplicate requests
  • 🌐 Network retries
  • ⏱️ Timeout replays
  • 💳 Double payments
  • 📦 Duplicate order creation

In distributed systems:

  • 🔄 Clients often retry requests
  • 🛡️ We must prevent repeated execution

3️⃣ What Breaks Without It?

Without idempotency:

  • 💳 Double payments
  • 📦 Duplicate orders
  • 🗄️ Duplicate database entries
  • ⚠️ Inconsistent system state

📌 Example:

User clicks "Pay" twice → money deducted twice ❌

4️⃣ When to Use / When NOT to Use

✅ When to Use Idempotency:

  • 💳 Payment APIs
  • 📦 Order creation

Especially important when:
🔄 Retries are possible

❌ When NOT Needed:

  • 👁️ Pure read operations
  • 📝 Temporary non-critical logs
  • 🧮 Stateless calculations

5️⃣ One Common Mistake

🚨 Confusing idempotent with safe.

Safe → No state change (GET)

Idempotent → May change state, but repeating doesn't change result further

Example:

  • 🗑️ DELETE is idempotent (deleting twice still deleted)
  • 📝 POST is usually NOT idempotent

🧠 HTTP Methods and Idempotency

Method Idempotent?
GET ✅ Yes
PUT ✅ Yes
DELETE ✅ Yes
POST ❌ No (usually)
PATCH ❌ Usually No

Example

  • GET /user/1
    Call 10 times → same result.
  • DELETE /user/1
    Delete once → user removed
    Delete again → still removed
    Same final state.
  • POST /create-order
    Call twice → two orders created ❌
    Not idempotent.

📊 HTTP methods and their idempotency properties

6️⃣ Real App Connection

💳 Payment System

  • Client sends payment request with idempotency key
  • If retried → server returns same response
  • No double charge

🛒 E-commerce

  • Order creation with unique request ID
  • Prevent duplicate orders

📊 Idempotency preventing duplicate operations in real systems

🎯 Interview-ready One-liner

Idempotency ensures that repeated execution of an operation produces the same result, preventing duplicate side effects in distributed systems.

So, Idempotent = safe to retry.

🧠 Summary

Idempotency is a crucial concept in distributed systems that ensures operations can be safely retried without causing unintended side effects.

It's essential for payment systems, order processing, and any operation where retries are possible.

Remember: Idempotent operations are safe to retry, non-idempotent operations require careful handling.

💡 Pro Tip

Always implement idempotency using unique request IDs or idempotency keys that clients generate and send with requests.

Common implementations: Database unique constraints, Redis for storing request results, or application-level idempotency tables.
