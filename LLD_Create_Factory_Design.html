🔷 Factory Design Pattern

Factory Pattern is a Creational Design Pattern.

Factory Pattern provides a central place to create objects and hides the object creation logic from the client.

Simply : Factory Pattern centralizes object creation in a factory class instead of letting clients create objects directly. It is especially useful when the exact object to create is determined at runtime, reducing coupling between the client and concrete classes (Implementation classes which contain business logic).

Instead of:

Java 
new UpiPayment();
new CardPayment();

the client asks a Factory:

Java 
Payment payment =
   PaymentFactory.getPayment("UPI");

The factory decides which object to create.

2️⃣ Problem (How Beginners Write Code)

1. Problem

Suppose you're building a payment application.

It supports:

  • UPI
  • Credit Card

A user can choose any payment method at runtime.

Code:

Java 
interface Payment {
   void pay();
}

class UpiPayment implements Payment {
   public void pay() {
       System.out.println("UPI Payment");
   }
}

class CardPayment implements Payment {
   public void pay() {
       System.out.println("Card Payment");
   }
}

CheckoutService class

Java 
public class CheckoutService {
   public void checkout(String type) {
    
       Payment payment;

       if(type.equals("UPI")) {
           payment = new UpiPayment();
       }
       else if(type.equals("CARD")) {
           payment = new CardPayment();
       }
       else {
           throw new RuntimeException();
       }

       payment.pay();

   }
}

🚨 Issues

1. Object Creation Mixed With Business Logic

checkout() method is doing:

  • Payment processing
  • Object creation

Two responsibilities.

Which is violation of SRP (Single responsible principle)

Imagine:

  • OrderService
  • UserService
  • CheckoutService
  • PaymentService

All of them contain:

Code 
if(paymentType.equals("UPI"))

Code duplication.

2. OCP Violation (Open Closed Principle)

Tomorrow:

WalletPayment new payment class

Need to modify:

CheckoutService class again.

3. Tight Coupling

Dependency 
CheckoutService
     ↓
UpiPayment
CardPayment

CheckoutService knows concrete classes (Implementation details classes).

Client is tightly coupled to implementations.

3️⃣ Factory Solution

Move object creation to a separate class.

Step 1: Product Interface

Java 
interface Payment {
   void pay();
}

Step 2: Concrete Products

Java 
class UpiPayment implements Payment {
   public void pay() {
       System.out.println("UPI Payment");
   }
}

class CardPayment implements Payment {
   public void pay() {
       System.out.println("Card Payment");
   }
}

class WalletPayment implements Payment {
   public void pay() {
       System.out.println("Wallet Payment");
   }
}

Step 3: Factory

Java 
class PaymentFactory {
   public static Payment getPayment(String type) {
       
       if(type.equalsIgnoreCase("UPI")) {
           return new UpiPayment();
       }
       if(type.equalsIgnoreCase("CARD")) {
           return new CardPayment();
       }
       if(type.equalsIgnoreCase("WALLET")) {
           return new WalletPayment();
       }
       throw new IllegalArgumentException(
               "Invalid Payment Type"
       );

   }
}

Step 4: Client

Java 
class CheckoutService {
   public void checkout(String type) {
       Payment payment = PaymentFactory.getPayment(type);
       payment.pay();
   }
}

Usage

Java 
public class Main {
   public static void main(String[] args) {
       CheckoutService service = new CheckoutService();
       service.checkout("UPI");
   }
}

Output:

Output 
UPI Payment

🎯 How It Solves Problem

Before:

Client decides:

Code 
new UpiPayment();
new CardPayment();
new PaypalPayment();

Client knows all classes.

After Factory

Client only knows only Payment interface:

Code 
Payment payment = PaymentFactory.getPayment("UPI");

Factory handles creation so, Which means Object creation centralized.

4️⃣ When To Use

1. Use factory when Object Creation Is Complex

Factory hides complexity.

2. Use factory when Client Should Not Know Concrete Classes

Client should only know:

  • Payment
  • Vehicle
  • Notification

Not:

  • UpiPayment
  • CardPayment
  • EmailNotification

3. Use factory when Many Implementations Exist

Notification

Implementations:

  • EmailNotification
  • SMSNotification
  • PushNotification
  • WhatsAppNotification

Factory becomes useful.

6. When NOT To Use

1. Only One Class Exists in entire application

Java 
Student student = new Student();

Factory is unnecessary.

2. Object Creation Is Simple

Java 
Book book = new Book();

Don't create:

Java 
BookFactory.getBook();

That's over-engineering.

7. Real World Examples

Payment Gateway

  • UPI
  • Card
  • Wallet
  • Net Banking

Factory returns correct payment processor.

Notification System

  • Email
  • SMS
  • Push Notification

Factory creates correct notification sender.

Remember: Spring Framework

Many Spring components internally use factory-based creation of beans through Spring Framework.

Difference between Singleton vs Factory

Singleton

✓
  • ✓Controls HOW MANY objects are created
  • ✓Ensures that a class has only one instance
  • ✓Provides a global access point to that instance

Factory

✓
  • ✓Controls WHICH object is created
  • ✓Centralizes object creation
  • ✓Decides which concrete object to create based on runtime requirements

🎯 Summary

Factory Pattern is a Creational Design Pattern that encapsulates object creation logic inside a factory class.

It solves the problem of clients directly creating concrete objects and becoming tightly coupled to them.

Instead of using new everywhere, the client asks the factory for an object, and the factory decides which implementation to create.

This improves maintainability, reduces coupling, supports OCP and DIP, and is widely used in frameworks and APIs.

Use it when multiple implementations exist and object creation logic needs to be centralized; avoid it when object creation is simple or only one implementation exists.
