Problem 9

🛒 Flash Sale Inventory Management: 10 Lakh Users, 2 Units

👉 Interviewer asks:

10 lakh people hit Buy Now at the exact same time during a flash sale. Only 2 units are left.
How did you handle this?

🎯 Problem Understanding:

The problem here is not inventory storage. It is concurrent reservation under extreme contention.

  • 👉 10 lakh users → competing for 2 units
  • 👉 Extreme load → system must handle gracefully
  • 👉 No overselling → exactly 2 users should get it

✅ Solution (Used by Amazon-like Systems)

🔥 Key Idea: Two-Layer Protection

👉 Fast layer (Redis) + Safe layer (Database)

1️⃣ Fast Gate (Using Redis)

💡 Implementation:

Keep stock in Redis:

stock = 2

When users click "Buy Now":

Use atomic operation:

DECR stock

The above step decreases the stock.

💥 What Happens:

Request Result
User 1 ✅ Success (stock → 1)
User 2 ✅ Success (stock → 0)
User 3+ ❌ Fail immediately

👉 Only first 2 users pass

🤔 Why Atomic Operation?

Atomic operations in Redis are required to prevent race conditions when multiple requests try to update the same stock simultaneously.

Without atomicity, concurrent reads and writes can lead to overselling.

So...

Atomic = Either fully happens OR doesn't happen — no interference where No other request can interrupt it

🛒 2️⃣ Soft Hold

📖 Definition:

Safe Hold = Temporarily reserving an item for a user for a short time

👉 It Means:

  • Item is not sold yet ❌
  • But no one else can buy it temporarily ✅

⏳ Example:

Hold for 5–10 minutes

  • If: Payment success → confirm order ✅
  • If: Payment fails → release stock 🔁

🤔 Why Soft Hold?

Because:

  • Users abandon cart
  • Payments fail
  • Network issues

👉 Without this → stock gets locked forever

💡 Summary of Soft Hold:

A safe hold is a temporary reservation of inventory for a user after they pass the initial check. It ensures that the item is not sold to others while the user completes the transaction, and is released back to the system for next user if the transaction fails or times out.

🗄️ 3️⃣ Database = Final Truth

At checkout or order confirmation, the DB uses optimistic or pessimistic locking to make sure the final stock transition is valid.

Only when you pay:

  • System checks again
  • Confirms purchase
  • 👉 This is final truth

💡 Why Database is Final Truth:

The database is considered the final source of truth because it ensures durability and consistency. While Redis is used for fast filtering and temporary reservations, the database performs the final validation and commits the transaction to guarantee correctness.

📋 Summary

To prevent overselling during a flash sale, I would use Redis as a fast gate with atomic decrement to allow only limited users. Then I would place items on temporary hold and finally confirm the purchase using the database to ensure correctness.

❓ Questions You May Get

🎯 Why Not Only Database?

👉 Because:
10 lakh people → DB crashes 😬

🎯 Why Not Only Redis?

👉 Because:
Redis is fast but not 100% safe

⚖️ So We Use Both

  • 👉 Redis = speed 🚀
  • 👉 DB = correctness ✅

🔍 Deep Dive: If 10 Lakh People Click at the Exact Same Millisecond, How Does the System Decide the First 2?

🔥 Key Idea:

In computers, nothing truly happens at the exact same time

Even if users click at the same millisecond:

👉 Requests reach server one by one (very very fast)

⚙️ How Order Is Actually Decided:

There is NO central "queue" created intentionally

Instead, order is decided by:

🔹 1. Network Travel Time (Most Important)

Each request travels from phone → server

Different users have:

  • different internet speeds
  • different distances

So even if they click at same time:

  • User A → reaches in 20ms
  • User B → reaches in 50ms
  • User C → reaches in 80ms

Order becomes: A → B → C

🔹 2. Load Balancer Routing

Requests first hit a load balancer.

It distributes requests to servers:

  • Server 1
  • Server 2
  • Server 3

Each server processes requests in its own order

🔹 3. Server Processing Time

Even inside server:

  • Requests handled in small batches
  • Slight delays happen
  • More ordering happens here

🔹 4. Redis Final Ordering (MOST CRITICAL)

All servers call Redis:

Redis processes:

  • One request at a time
  • In the exact order it receives

👉 This is the final queue

🧠 Interview Tips

  • Start with the core problem — Concurrent reservation, not storage
  • Explain the two-layer architecture — Redis for speed, DB for correctness
  • Emphasize atomic operations — Critical for preventing race conditions
  • Don't forget soft hold — Prevents stock from being locked forever
  • Explain ordering clearly — Network + Load Balancer + Server + Redis
  • Know the trade-offs — Why not just Redis? Why not just DB?
