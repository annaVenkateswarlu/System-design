Interface Segregation Principle

ISP - Fourth Principle of SOLID

Home / LLD / Interface Segregation Principle

Have you ever implemented an interface... only to realize you had to write empty methods just to make the compiler happy?

Or updated a shared interface... and suddenly watched multiple unrelated classes start breaking?

If so, you have probably run into a violation of one of the most misunderstood design principles in software engineering: the Interface Segregation Principle (ISP).

🔷 Interface Segregation Principle (ISP)

ISP is the fourth principle of SOLID.

It states:

Clients should not be forced to depend on methods (in interface) they do not use.

In simple words:

Don't create large interfaces with unrelated methods.

Create small, focused interfaces instead.

Prefer many small, focused interfaces over one large interface.

❌ Example 1 (Violates ISP)

Suppose we create:

Java 
interface Worker {
    void work();
    void eat();
    void sleep();
}
Java 
class HumanWorker implements Worker {
    
    public void work() {
        System.out.println("Working");
    }
    public void eat() {
        System.out.println("Eating");
    }
    public void sleep() {
        System.out.println("Sleeping");
    }

}

class RobotWorker implements Worker {

    public void work() {
        System.out.println("Working");
    }

}

🚨 Problem Explanation

A robot:

  • Can Work ✅
  • Can Eat ❌
  • Can Sleep ❌

But the interface forces it to implement all methods.

This is an ISP violation.

Why This Is Bad

The interface says:

Interface Tree Java 
Worker
├── work()
├── eat()
└── sleep()

We know the rule of interfaces:

Every class implementation must support all methods mentioned in the interface.

But:

Human work + eat + sleep
Robot only work

When you see throw new UnsupportedOperationException(); inside interface implementations, it's often a sign that ISP is being violated.

✅ Example 1 (Follows ISP)

Split the interface into multiple small interfaces.

Java 
interface Workable {
    void work();
}

interface Eatable {
    void eat();
}

interface Sleepable {
    void sleep();
}

class HumanWorker implements Workable, Eatable, Sleepable {

    public void work() {
        System.out.println("Working");
    }

    public void eat() {
        System.out.println("Eating");
    }

    public void sleep() {
        System.out.println("Sleeping");
    }

}

class RobotWorker implements Workable {

    public void work() {
        System.out.println("Working");
    }

}

Output

Human is working

Human is eating

Human is sleeping

Robot is working

🧠 Real-World Example

❌ Bad

Java 
interface SmartDevice {
    call();
    takePhoto();
    printDocument();
}
  • Phone can do all three.
  • Printer cannot make calls.
  • Camera cannot print documents.

Forced implementations are bad design.

✅ Good

Java 
interface Callable
interface CameraCapable
interface Printable

Each device implements only what it needs.

ISP and LSP Connection

Notice this code:

Java 
void eat() {
    throw new UnsupportedOperationException();
}

You saw the same thing in LSP.

That's often a clue that:

  • ISP is violated (interface too big)
  • LSP may also be violated (child can't honor contract)

🎯 Benefits

Smaller Interfaces Easier to understand
Less Coupling Classes depend only on needed methods
Better Flexibility Implement only required behavior
Easier Maintenance Changes affect fewer classes

Summary

We know Interface Rule: A class must implement all methods of the interface it implements.

The Interface Segregation Principle states that no class should be forced to implement methods it does not use. Large interfaces should be split into smaller, focused interfaces.

ISP says that we should keep interfaces small and focused so that classes are not forced to implement methods they don't need.
